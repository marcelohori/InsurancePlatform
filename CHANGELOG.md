# 📜 Histórico do Projeto

Linha do tempo da evolução do schema e das principais entregas do InsurancePlatformV01, reconstruída a partir das migrations do Entity Framework Core e do histórico de commits do repositório. Para o detalhamento de decisões arquiteturais, veja [ARCHITECTURE.md](ARCHITECTURE.md).

## 2026-09-09

- **Proposta** — `AddCriadoPorDateCreationIndex`: índice composto (`CriadoPor`, `DataCriacao`) para acelerar a listagem paginada de propostas por usuário.
- **Proposta** — `AddIndexesAndConstraints`: índice em `DocumentoSegurado` e check constraints (`valor_cobertura >= 0`, `valor_premio >= 0`).
- **Contratacao** — `AddIndexesAndConstraints`: índice único em `NumeroApolice`, índice em `PropostaId` e check constraint (`valor_premio >= 0`).
- **Analise** — `AddIndexesAndConstraints`: índice único em `PropostaId` (uma análise por proposta) e check constraint (`score_risco` entre 0 e 100).
- **Proposta** — `AddPropostaOwner`: coluna `criado_por` para suportar a regra "usuário só vê/edita as próprias propostas" (exceto `analista`/`admin`).
- Correção do filtro global de `FluentValidation` (`FluentValidationFilter`): o registro de validators via `AddValidatorsFromAssembly` apontava para o assembly da API em vez do assembly `Application` onde os validators residem — os validators nunca eram encontrados pelo DI. Corrigido em Proposta.Api e Contratacao.Api.
- Correção de `CriarPropostaCommandValidator`/`AtualizarPropostaRequestValidator`: a validação de `TipoSeguro` usava uma lista de valores divergente do enum de domínio (`TipoSeguro { Auto, Vida, Residencial, Saude }`); substituída por `Enum.TryParse<TipoSeguro>`.
- Suíte de testes consolidada em **125 testes** (unit + integration + architecture) — 0 falhas.
- Novo endpoint **dev-only** `POST /api/dev/auth/token` no Proposta.Api (`src/Proposta/Proposta.Api/Endpoints/DevAuthEndpoints.cs`), mapeado só em `IsDevelopment()`, para gerar JWTs de teste sem precisar de jwt.io — com 3 testes de integração cobrindo o fluxo.
- Corrigido `.env.example`: o placeholder de `JWT_SIGNING_KEY` era, por coincidência, exatamente o valor que o guard de startup de cada API rejeita de propósito — trocado por um placeholder que não colide com o bloqueio.
- Adicionado `docker-compose.local.yml` (overlay opt-in via `-f`) expondo as portas de Postgres/RabbitMQ ao host, para permitir rodar os serviços com `dotnet run` fora da rede Docker sem alterar o comportamento seguro-por-padrão do `docker-compose.yml` principal.
- Seção "Sem Docker" do README reescrita e validada rodando os três serviços simultaneamente contra a infraestrutura Dockerizada (fluxo completo Proposta → Analise (evento) → Contratacao (HTTP síncrono) testado manualmente com sucesso), incluindo o alerta sobre `RunMigrationsOnStartup=true` exigir um role com permissão de DDL (não o role `*_app`, que só tem DML).
- Swagger UI (`Swashbuckle.AspNetCore.SwaggerUI`) adicionado às três APIs, mapeado apenas em `Development`, servindo a UI sobre o documento já gerado por `Microsoft.AspNetCore.OpenApi` (`/openapi/v1.json`). Inclui um `IOpenApiDocumentTransformer` (`BearerSecuritySchemeTransformer`) que declara o esquema JWT Bearer no documento, habilitando o botão "Authorize" da UI.
- Removido `.ExcludeFromDescription()` do endpoint `POST /api/dev/auth/token` (deixava ele fora do documento OpenAPI e, portanto, invisível no Swagger UI) — agora aparece agrupado sob a tag "Dev".
- `docker-compose.local.yml`: porta do Postgres exposta ao host mudou de 5432 para **5433**, para não colidir com qualquer outra instância de Postgres já rodando na porta padrão da máquina do desenvolvedor (sintoma do conflito: o container do projeto fica preso em `Created` com "port is already allocated", e qualquer `dotnet run` do Migrator/API falha com "password authentication failed" porque a conexão cai em um Postgres alheio na 5432). README atualizado com a porta nova e uma nota explicando o sintoma.
- **Provedor de IA plugável e opcional**: `IRiskAssessmentPort` (a porta de saída já existente) ganhou um segundo adaptador, `GroqRiskAssessmentAdapter`, usando a API da Groq (compatível com OpenAI, tier gratuito, sem cartão) como alternativa gratuita ao Claude/Anthropic para testes locais. A escolha é feita por configuração (`Analise:Provider` = `Anthropic` (default) | `Groq`), validada apenas para o provedor selecionado. O prompt e a validação da resposta JSON (score/recomendação/justificativa) foram extraídos para `RiskAssessmentJsonContract`, compartilhados pelos dois adaptadores. Inclui 3 novos testes de integração (`GroqRiskAssessmentAdapterTests`, via WireMock) — suíte total agora em **131 testes**.
- Modelo padrão da Groq corrigido de `llama-3.3-70b-versatile` (removido do catálogo da Groq, retornava `404 model_not_found`) para `openai/gpt-oss-20b` e, em seguida, para **`qwen/qwen3.8-27b`** — o `gpt-oss-20b` é um modelo de raciocínio (chain-of-thought) que falhava a validação de JSON da própria Groq de forma intermitente (~1 em cada 3 chamadas, com `400 json_validate_failed`); o `qwen3.8-27b` não tem essa etapa de raciocínio e, em testes repetidos (7/7 chamadas reais), sempre retornou JSON válido, além de ser mais rápido.
- `ProcessarAnaliseUseCase` engolia qualquer exceção do provedor de IA sem logar nada (só persistia a mensagem genérica em `AnaliseRisco.Justificativa`) — dificultou diagnosticar a falha intermitente da Groq. Adicionado log de erro (via `[LoggerMessage]`, mantendo `CA1848`/`TreatWarningsAsErrors`) antes de marcar a análise como `Falha`, sem alterar o comportamento de não bloquear o fluxo da proposta.
- **Correção de bug real em `DomainExceptionHandler`** (Proposta.Api, Contratacao.Api, Analise.Api): as respostas de erro eram escritas via `IProblemDetailsService.TryWriteAsync`, cujo writer JSON recusa escrever o corpo (`Detail`/extensões) quando o `Accept` da requisição não inclui `application/json` — exatamente o que o Swagger UI manda por padrão (`Accept: text/plain`). Na prática, todo erro de negócio (CPF inválido, proposta não encontrada, etc.) testado pelo Swagger UI voltava como um `ProblemDetails` genérico vazio (`{type, title: "Bad Request", status}`), escondendo a causa real. Corrigido escrevendo o JSON diretamente via `HttpResponse.WriteAsJsonAsync(..., contentType: "application/problem+json")`, ignorando a negociação de conteúdo do cliente — a API sempre devolve o detalhe do erro agora, não importa o `Accept` enviado. Também simplificado: a checagem de tipo duplicada (`is not X and not Y and not Z` + switch) virou um único `switch` com `_` como fallback. Novo teste de regressão (`ErrorResponseContentNegotiationTests`) — suíte total agora em **132 testes**.
